# Combined driver verification

The `combined` profile is a packaging step toward the [JVM-first GDAL coverage goal](../GDAL_SUPPORT.md). Linux x64 glibc producer, isolated publication and actual runtime verification were completed in PR38; macOS ARM64 followed in PR40 with its owned PostGIS server. Linux ARM64 has separate cross-build and actual runtime CI phases, pending their current evidence. Windows x64 combined coverage also remains pending. No complete GDAL coverage or performance improvement is claimed.

## Distribution and CI scope

The profile combines the existing scientific HDF5/netCDF4, Parquet/Arrow, native HTTP/TLS and PostgreSQL capabilities in one dependency closure. It uses its own prepared source tree, engine fingerprint, installed dependencies and local Maven version, `0.1.0-combined-SNAPSHOT`. The small default distribution and the seven isolated profile jobs retain their existing roles.

The optional-profile workflow retains `Profile combined on linux-amd64` beside the isolated PostgreSQL job and adds `Profile combined on macos-arm64`. Linux database cells use the pinned disposable `postgis/postgis:16-3.5` container. The Mac cell uses the versioned PostGIS provider lock and an owned fresh data directory, allocated loopback port and server process; it does not start a machine service. A password-free DSN is generated for that fixture, while its mode0600 `PGPASSFILE` is private and inherited only by child processes. Both combined cells install pinned h5py/numpy fixture dependencies. The Mac combined cell also provisions modern Bison for its Parquet dependency.

Each cell runs one default-engine size baseline followed by its isolated profile verification. Cache keys and artifact names include profile and target. `driver-profile.py` keeps its loopback HTTP/TLS fixtures alive through all tests and diagnostics, then closes them before reporting final request logs. On Mac it also owns the PostGIS context and requires its completed shutdown receipt before reporting; Linux container teardown remains owned by the CI job. Public Mac fixture failure receipts remain available when preparation or tests fail.

The Linux and Mac cells require actual source JVM and host Native tests plus independent published JVM and Native consumers. JVM remains the first complete-support target; these host Native checks do not establish combined coverage on other Native targets.

Linux ARM64 adds an x64 cross producer and an `ubuntu-24.04-arm` execution job. The first job links both Native test executables, cross-compiles the IPC/cache probes and publishes the isolated eight-coordinate Maven repository. A complete hashed transport preserves prepared sources, engine payloads, executables and compile-only receipts. The second job verifies its exact Git/source/engine identities and actual AArch64 executable formats, then runs normal source/published JVM tests and both unchanged Native executables. A test-only immutable JSON configuration supplies fresh runtime-host fixtures; missing, partial or non-loopback settings fail before fallback. Seven process markers bind four fixture contexts and three fresh combined JVMs to those exact endpoints. The Native runtime receipt includes the actual command, PID, exit and complete raw test output; no XML is synthesized and the independent compile-only receipt remains unchanged.

The ARM PostGIS provider starts from an exact official PostgreSQL ARM64 image and 83 hash-locked additional DEBs, installed offline in its own container. Acceptance binds all 227 installed package versions, four actual ARM64 provider binaries, server/extension identity, POINT readback from a new connection, exact table deletion and terminal server/container/volume cleanup. PostgreSQL listens inside the bridge container while only its allocated host loopback port is exposed. Provider dependencies stay inside the separate fixture container. Private credentials, PGDATA, DEBs and image layers are excluded from evidence uploads; the public receipt and command outputs are retained even on failure.

## Acceptance evidence

All combined capabilities must be exercised through the same runtime and packaged engine in each fixture context. Driver registration alone is insufficient. The combined fixture must retain the existing real-data assertions and verify cross-driver conversion without switching engines:

- Closed HDF5 input and actual OS-path NC4 conversion/readback, including exact wide integers, complex and string values, typed NoData, attributes, units, scale and offset.
- Parquet field and geometry readback plus the packaged Arrow IPC regression.
- HTTP bounded ranges, validators, retry/deadline/cancellation, TLS trust/hostname rejection, sidecars and the native cache/registry regression.
- Disposable PostgreSQL/PostGIS create, write, read and delete, including field values and geometry coordinates. Cleanup must remove only the test's own table and outputs.
- Representative transfers between these capabilities in the same process, with explicit source/result ownership.

Current API cases, multidimensional conversion and dimension lifetime checks must also pass in source and independent published consumers. The source hash inventory, prepared profile identity, actual packaged JVM class/source/native bytes, isolated Maven coordinates, native dependency audit, size/gzip measurements and relevant raw execution results must match the current source. A passing isolated profile cannot substitute for this combined evidence.

## Retained diagnostics and limits

Profile artifacts contain the measured report and isolated local Maven archive. Evidence artifacts retain actual XML, request logs, public fixture certificates, prepared-source hash receipts and the generated profile fixture/probe Kotlin sources. The workflow also selects the seven `HttpMemoryProbe*.class` files, `CombinedDriverMemoryProbe*.class`, the generated `DriverProfileApiTest*.class`/`DriverProfileApiTestKt*.class` and `DriverProfileFixtures*.class` files, their `DatasetApiTestKt*.class`/`DatasetOutputPathKt*.class` helpers, and the `gdal4k_http_probe`/`arrow-ipc-check` executables so their actual bytes can be checked when those files were produced. Missing optional outputs must be recorded; an upload pattern alone does not establish that the bytes exist.

Mac and ARM Linux evidence additionally retain public PostGIS receipts and sanitized command logs, including preparation failures. Successful acceptance requires the respective pinned provider identity, current manager/lock hashes, actual provider executable hashes and ARM64 architecture, verified data directory/extension/version, successful owned stop, closed port and exited postmaster. Passwords, passfiles, PGDATA and provider build inputs stay outside artifact paths; the fixture server is not part of the published GDAL engine.

Fresh-JVM HTTP diagnostics retain stdout, whole-process OS RSS logs, request logs and the deterministic fixture. Cumulative JVM allocation, sampled heap and OS RSS remain separate measurements. Adding optional dependencies and reporting their size does not establish a speed or memory improvement. No WAN/TLS performance, universal, Native/Android performance, zero-copy, streaming or total-memory-bound claim follows from these diagnostics.

The combined diagnostic starts three fresh JVMs sequentially. Each process selects one combined JNI library and keeps one runtime for one warmup plus three measured rounds. Every measured round includes the cross-driver conversions, exact value/geometry readback, assertions and owned file/table cleanup. Runtime initialization, the warmup and final runtime shutdown are outside elapsed/allocation measurements; whole-process OS RSS includes them. The reporter retains stdout and native `/usr/bin/time` output: Linux uses `-v` and converts peak RSS from KiB to bytes; Darwin uses `-l`, whose maximum resident set size is already bytes. Cumulative allocation covers JVM threads; the 2ms heap sampler can miss brief peaks, and native allocations are outside those JVM counters. These small-fixture integration measurements are functional diagnostics, with no throughput or before/after improvement claim. They require their own source/probe/class/engine and raw-log bindings and do not reuse the earlier isolated-profile measurements as a performance baseline.

Whole-process RSS covers the JVM and its native engine. Separate HTTP/TLS fixture servers, the Linux disposable PostGIS container and the owned Mac PostGIS process are outside that JVM and their memory is excluded.

The primary Web workflow retains the per-target `related-inputs-js` and `related-inputs-wasmJs` result directories, alongside its existing execution logs. This corrects the earlier mismatch between the generated result paths and the artifact pattern; it does not replace actual Node/Chromium execution.
